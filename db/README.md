# Database artifacts

Everything in this folder except the two guides (`README.md`, `PORTABILITY.md`) is GENERATED by `pnpm db:sync` from the migrations in `supabase/migrations/`. Do not edit generated files by hand; change the schema with a new migration.

No running database is needed, locally or in the cloud. `pnpm db:sync` applies the migrations to an in-memory Postgres inside Node (PGlite, with a shim for the Supabase roles and the `auth` and `storage` schemas), reads the result and throws the database away. It takes a few seconds and needs no Docker.

| Path | Content | Used for |
|---|---|---|
| `schema/master-schema.sql` | `pg_dump --schema-only` of every application schema (Supabase platform schemas excluded) | Reviewing the current schema in one file; recreating it on any Postgres |
| `schema/schema.dbml` | Engine-neutral model (tables, columns, keys, indexes, enums, references) | Diagrams (dbdiagram.io), conversions with `@dbml/cli` |
| `schema/portable/mysql.sql`, `sqlserver.sql`, `sqlite.sql` | Starting-point DDL for other engines, with stub tables for Supabase-managed references | Moving to another SQL service |
| `schema/.migrations-hash` | Fingerprint of `supabase/migrations/*` at the last sync | Hooks and CI detect stale artifacts |
| `export/queries/NNN_<schema>.<table>.sql` | One explicit SELECT per table, portable text output, in foreign-key load order | Exporting data to CSV (`pnpm db:export`) or reading it with any client |
| `export/manifest.json` | Load order, primary and foreign keys, source types and portable types per engine, CSV conventions | Writing importers for other engines |
| `portability/supabase-dependencies.md` | Inventory of Supabase-specific constructs in use (auth references, RLS helpers, storage, realtime, functions, edge functions, grants) | Planning a migration off Supabase |
| `export/out/` | CSV exports (gitignored, may contain personal data) | Data transfer |

## Workflow

```bash
pnpm supabase migration new add_invoices    # creates supabase/migrations/<timestamp>_add_invoices.sql (no Docker)
# write the SQL (database-architect). When the file is saved, the harness runs pnpm db:sync
# automatically and reports either "applies cleanly" or the failing file and line.
pnpm db:test                                # pgTAP tests (RLS, constraints, harness guards), offline
git add supabase/migrations db src/types/database.types.ts
```

| Command | What it does |
|---|---|
| `pnpm db:sync` | Rebuilds every artifact in this folder and `src/types/database.types.ts` from the migrations; validates the migrations and `supabase/seed.sql` |
| `pnpm db:check` | Same, then fails if anything differs from the committed files (CI) |
| `pnpm db:test` | Runs `supabase/tests/database/*.test.sql` with pgTAP against the in-memory database |

CI runs `pnpm db:check` and `pnpm db:test` in the quality job, and additionally applies the migrations and seed to a real Supabase stack on the GitHub runner (pgTAP and security advisors) as a safety net.

## Limits of the offline build

- It runs Postgres 18 (PGlite); Supabase runs Postgres 17. Avoid Postgres 18-only syntax; the CI job on real Supabase catches it.
- Extensions: common ones (pgcrypto, uuid-ossp, pg_trgm, citext, hstore, ltree, unaccent, btree_gin/gist and others) run for real; `vector` needs `pnpm add -D @electric-sql/pglite-pgvector`; `pg_cron`, `pg_net`, `supabase_vault` and `pg_graphql` are stubbed (their functions exist, nothing runs); others are skipped with a note.
- The Supabase shim (`scripts/db/lib/supabase-shim.sql`) models the platform objects migrations usually reference. Extend it if a migration needs another one.
- Running the app (`pnpm dev`) needs a Supabase project: put its URL and publishable key in `.env.local`. New migrations reach that project through the `db-deploy` workflow after merge, or when the human runs `pnpm supabase db push` against a dev project.

## Rules

- Migrations are forward-only and immutable once committed (hooks enforce it).
- Every table in `public` has RLS enabled with explicit policies (hooks and the pgTAP guard test enforce it).
- Supabase-specific constructs are allowed when justified; they show up automatically in the dependency inventory.
- See `PORTABILITY.md` for moving the schema and data to another SQL service.
